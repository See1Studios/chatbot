## 1. 범위 / 비목표

**범위**: 배포판의 개인화 단계(① 콘텐츠 ② 규칙 + 에이전트의 자기 개발), 각 단계의 저장 위치·편집 주체·승인·되돌리기, 에이전트가 돕는 흐름, 공통 뼈대(변경 기록과 되돌리기, 제안 카드).

## 4. 설계 초안

### 4.1 사다리와 규칙

| 단계 | 층 | 편집 | 에이전트 변경 | 되돌리기 |
|---|---|---|---|---|
| ① 콘텐츠 | 캐릭터 카드, 외형, 로어북 | 사용자 UI + 에이전트 | **제안 카드**(사용자 승인 후 반영) | 스냅숏 |
| ① 콘텐츠 | 기억(공용·캐릭터별) | 사용자 UI(보기·고치기·잊기) + 에이전트 | **바로 반영하되 보이게**(방금 기억한 것을 알림, 한 번에 되돌리기) | 스냅숏 |
| ① 콘텐츠 | 사적 기억 | 에이전트 자동 요약 + 사용자 UI | 바로 반영, 사적 모드 안에서만 보임 | 스냅숏(기기 밖으로 나가지 않음) |
| ② 규칙 | 지침, 역할 팩, 팀·두뇌, 사적 규칙 | 사용자 UI + 에이전트 | **제안 카드** | 스냅숏 |
| ② 규칙 | 스킬 | 에이전트가 작성·다듬기, 사용자 켜기/끄기 | **제안 카드**(새 스킬·변경) | 스냅숏 |

원칙:
- 에이전트는 **바꾸기 전에 보여 준다.** 기억만 예외로 바로 쓰되, 쓴 사실을 보이게 하고 즉시 되돌릴 수 있게 한다(대화 흐름을 끊지 않기 위해).
- 모든 변경은 **되돌릴 수 있다.** 층에 상관없이 같은 방식으로.
- 모든 결과물은 **표준 형식**으로 저장한다(ST 카드 V2, `SKILL.md`, JSON). 나중에 방향이 바뀌어도(시장 검토 등) 데이터가 갇히지 않는다.
- 개인화가 두꺼워져도 **토큰 비용이 따라 불지 않게**: 지침 묶음 예산(`bundle_budget.json`) 안에서, 넘치는 부분은 로어북·검색으로 필요할 때만 불러온다.

### 4.2 공통 뼈대 ① — 변경 기록과 되돌리기

- 모든 층의 쓰기는 **한 함수**를 거친다: 이전 판을 `$CHATBOT_DATA/history/<층>/<대상>/<시각>`에 스냅숏으로 남기고, 변경 기록 한 줄(`층·대상·작성자(user|agent)·이유·시각`)을 쓴 뒤 반영한다.
- 되돌리기 = 이전 스냅숏으로 같은 함수를 통해 다시 쓰기(되돌리기도 기록된다).
- 보존: 층별 최근 N개(설정값) + 사용자가 고정한 판. 사적 층의 스냅숏은 사적 층과 같은 보호(암호화 계획을 따른다, release-pipeline 사적 보호).
- 지금의 지침 백업(`workspace_status.py::_backup`)을 이 함수로 흡수한다.

### 4.3 공통 뼈대 ② — 제안 카드

- 에이전트가 층을 바꾸고 싶으면 **제안**을 만든다: `무엇을(층·대상) · 왜(대화 근거) · 전/후 미리보기`.
- 화면에는 선택지 채널로 카드가 뜬다: **적용 / 고쳐서 적용 / 거절**. 적용하면 4.2 함수로 반영.
- 엔진 쪽 저장은 관찰 기록을 재사용하되, 사용자에게는 「티켓」이라는 개발 용어를 쓰지 않는다. 개발판에서는 코드 변경이 지금처럼 티켓으로 간다.
- 제안이 쌓이지 않게: 같은 대상의 제안은 하나로 합치고, 한 번에 보이는 수를 제한한다(티켓의 `MAX_PROPOSED`와 같은 발상).

### 4.4 에이전트가 돕는 흐름 (첫 후보)

| 흐름 | 사용자 말 예 | 에이전트가 하는 일 | 쓰는 것 |
|---|---|---|---|
| 캐릭터 만들기 인터뷰 | 「나만의 캐릭터 만들고 싶어」 | 질문 몇 개로 성격·말투·관계 온도를 잡고 카드 초안을 제안 | 카드 편집기, 제안 카드 |
| 말투·성격 다듬기 | 「좀 더 장난스럽게」 | 카드의 해당 부분을 바꾼 전/후를 제안 | 제안 카드 |
| 외형 만들기 | 「옷 바꿔 줘」「이런 느낌으로 그려 줘」 | 이미지 프로바이더로 초안 → 규격 검사 → 적용 제안 | `character-art` 스킬의 배포판판, `check_character_art.py` |
| 기억 정리 | 「나에 대해 뭘 기억해?」「그건 잊어」 | 기억을 보여 주고 고치거나 잊기 | 기억 화면, `memory` 도구 |
| 스킬 배우기 (Hermes식) | (같은 요청이 반복됨) | 반복 절차를 스킬로 정리해 제안 | 관찰 → 스킬 제안 |
| 가져오기 | ST 카드·로어북 파일 | 가져와서 부족한 부분(외형·두뇌)을 채우자고 제안 | ST 가져오기, 제안 카드 |

결과물은 원하면 플러그인 패키지로 내보낸다([plugin-architecture.md](plugin-architecture.md) `plug/F`).

## 7. 의존·순서·리스크

```text
uds (~/.pe) → B(변경 기록·되돌리기) → C(카드·로어북·팀) ─┬→ E(제안 카드) → F(스킬 제안) · G(인터뷰)
                                   └→ D(기억 화면)   ──┘
```

- 리스크: 에이전트의 제안이 많아지면 피로해진다 → 합치기·개수 제한(4.3), 기억은 조용히(4.1).
- 리스크: 사적 층의 스냅숏이 보호 없이 쌓이면 「들키면 안 되는 대화」 원칙이 깨진다 → 사적 보호(잠금·암호화)와 같은 규칙.
- 리스크: 개인화가 두꺼워질수록 지침이 길어진다 → 묶음 예산 안에서, 넘치는 부분은 로어북·검색으로.
- 되돌릴 수 있는 설계: 표준 형식 저장 + 모든 변경의 스냅숏 덕분에, 나중에 방향을 바꿔도 사용자 데이터는 그대로 옮겨 간다.
