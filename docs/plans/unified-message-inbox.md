# 통합 메시지 — 텔레그램식 대화·업데이트·읽은 위치

> 방향 (align/D, 2026-10-01): **핵심** — 새 중앙 시스템을 짓지 않고, 이미 있는 저장소 위에 현대 메신저(텔레그램)의 대화·업데이트·읽은 위치 구조를 얹는다. 1:1 대화가 다른 방의 글로 오염되지 않게 한다
> 상태: **active** (2026-10-02 개정: 텔레그램 구조로 다시 씀. 본문은 대화 저장소에, 이벤트 대장에는 가리키는 줄만)
> 목적: 사용자와 캐릭터의 1:1, 단체방, 캐릭터끼리의 1:1, 작업·시스템 알림을 메신저 한 벌의 규칙으로 다룬다. 참여자 중 사람은 운영자 한 명이고 나머지는 AI라는 점만 예외로 둔다.
> 관련: [character-events-and-rooms.md](character-events-and-rooms.md)(이벤트 종류·수취인, 방) · [ux-shell-roadmap.md](ux-shell-roadmap.md)(UX8, 읽음 표시 없음, `ux/S7` 답장) · [private-security.md](private-security.md) · [CONCEPT.md](../CONCEPT.md)

## 원칙

대화의 종류(사용자↔캐릭터 1:1, 단체방, 캐릭터끼리 1:1)는 **창구가 하나**다. 대화 id, 글 모양, 안 읽음, 보내기·불러오기가 종류와 상관없이 같고, 단체방만의 배달 경로를 따로 두지 않는다. 저장소는 종류마다 지금 것을 쓴다. 텔레그램도 1:1·작은 그룹과 슈퍼그룹·채널의 서버 저장 방식이 다르지만, API는 하나다. 1:1의 저장소는 세션 기록이고, 제공자가 바뀌어도 그대로 이어지므로 옮기지 않는다.

텔레그램의 기본 구조를 그대로 쓴다. 다르게 하는 것은 아래 "AI라서 다른 점" 표에 있는 것뿐이고, 표에 없는 차이는 만들지 않는다. 화면 쪽 예외(읽음 표시 없음, 입력 중 표시 없음)는 [ux-shell-roadmap.md](ux-shell-roadmap.md) UX8을 따른다.

## 텔레그램 구조와 엔진의 대응

| 텔레그램 | 뜻 | 엔진에서 |
|---|---|---|
| dialog (peer) | 대화 하나. 1:1이든 그룹이든 같은 모양 | 대화 id: 사용자↔캐릭터는 그 캐릭터의 세션 체인, 단체방은 방 id, 캐릭터↔캐릭터는 `dm:<a>:<b>`(두 id를 정렬) |
| message store | 대화마다 하나의 기록. 글 번호는 그 대화 안에서 증가 | 사용자↔캐릭터: 지금의 세션 기록 그대로. 방: `room_chat` 방 로그 그대로. 캐릭터↔캐릭터: 방 로그와 같은 형식의 대화 로그 |
| message | `id`, `from_id`, `date`, `message`, `reply_to_msg_id`, 멘션 entity | 방 로그 한 줄 `{n, ts, who, text, mentions}` + 선택 `reply_to`(같은 대화의 `n`). 기존 키는 바꾸지 않는다 |
| update 순번(`pts`) + `getDifference` | 계정마다 "무엇이 바뀌었나"의 순번 기록. 꺼져 있던 기기는 마지막 순번 이후만 받아 따라잡는다 | `events.publish`의 `msg.new` 줄 `{conversation, n, from}`. **본문은 싣지 않는다**(이벤트 계획의 결정 그대로) |
| `read_inbox_max_id` | 대화마다 "내가 여기까지 읽었다" | (캐릭터, 대화)마다 읽은 `n` 하나. 세션 id가 아니라 캐릭터 기준이라 새 세션이 생겨도 안 읽은 글이 남는다 |
| `unread_count`, `unread_mentions_count` | 대화 목록의 안 읽음 수, 나를 부른 수 | 읽은 `n` 다음 글 중 내가 보내지 않은 것의 수, 그중 나를 멘션한 것의 수. 저장하지 않고 계산한다 |
| `messages.getHistory` | 대화를 열면 최근 글을 불러옴 | 캐릭터용 도구 하나: 대화 id를 주면 최근 글을 돌려주고 읽은 위치를 당긴다 |
| `messages.sendMessage` | 보내기 하나. 답장은 `reply_to` | 캐릭터용 도구 하나: 대화, 본문, `reply_to`. 보내는 이가 그 대화의 참여자인지 검사한다 |
| 그룹의 봇 privacy mode | 그룹의 봇은 자기를 부른 글과 자기에게 단 답장만 받음 | 방의 발언자 선택(`room_chat.pick`, E4)이 이미 이 역할을 한다. 바꾸지 않는다 |
| 1:1의 `@이름` | 이름 링크일 뿐이고, 그 사람에게 배달되지 않는다 | 같다. 전하려면 그 사람과의 대화에 보낸다(아래) |
| secret chat | 같은 상대와 따로 있는 비밀 대화. 일반 대화와 기록이 섞이지 않음 | 사적 모드 세션. 이미 따로 있다([private-security.md](private-security.md)) |
| 업데이트 푸시 | 앱이 켜져 있으면 바로, 꺼져 있으면 다음에 열 때 | 화면: 지금 있는 SSE로 대화 목록의 안 읽음을 민다(`inbox/E`). 캐릭터: 다음 턴 앞에서 따라잡는다 |

## AI라서 다른 점

| 무엇 | 텔레그램 | 여기 | 이유 |
|---|---|---|---|
| 클라이언트가 켜져 있는가 | 늘 켜져 있고 푸시를 받는다 | 캐릭터는 턴이 돌 때만 깨어 있다. 턴 앞에서 `getDifference`에 해당하는 따라잡기를 한다 | 두뇌 호출은 턴 단위다 |
| 따라잡기에 무엇을 싣나 | 앱은 대화 목록과 미리보기를 받는다 | 턴 앞 안내에는 대화 목록 한 줄만 싣는다("안 읽음: 대화 A 1 · 업무방 3(나를 부름 1)"). 본문은 캐릭터가 도구로 연다 | 다른 대화의 본문이 지금 대화에 섞이지 않게 하려는 이 계획의 목적, 토큰 |
| 읽음 표시, 입력 중 | 있다 | 화면에 없다 | UX8, 운영자 결정 2026-09-29 |
| 남의 1:1을 볼 수 있나 | 못 본다 | 캐릭터끼리의 1:1을 운영자가 볼지는 D8 | 참여자 중 사람은 운영자뿐이고 캐릭터는 운영자의 것이다 |
| 한 사람에 머리가 몇 개인가 | 사람 하나가 여러 기기에서 읽는다. 한 기기에서 읽으면 모두 읽음 | 캐릭터 하나에 두뇌(세션)가 여럿이다: 업무, 방 자리, 사적. 읽은 위치를 둘 둔다: 캐릭터의 읽음(안 읽음 수·배지, 텔레그램 그대로)과 세션마다의 "이 두뇌가 본 곳". 새 세션은 캐릭터의 읽음에서 시작한다 | 방 세션이 읽은 글을 업무 세션 두뇌는 모른다 |
| 누가 보냈나 | 서버가 로그인한 계정으로 안다 | 도구 서버가 호출한 세션을 안다(`inbox/0`): 호스트가 연결을 연 프로세스의 족보를 거슬러 자기가 띄운 에이전트 프로세스를 찾는다(`mcp_caller.py`, `session.caller_session`). HTTP 두뇌는 호스트 자신이 부르므로 헤더로 세션을 대고, 호스트는 자기 프로세스의 연결에서만 그 헤더를 믿는다. 모델이 넘긴 "보내는 이" 값은 믿지 않는다 | 어댑터마다 도구 설정이 작업공간의 공용 파일이라 세션마다 다른 값을 실을 수 없다. 족보는 OS 사실이라 제공자와 상관없다 |
| 읽은 것을 기억하나 | 화면에 남아 있다 | 대화 저장소에 남는다. 두뇌가 잊어도(HTTP 두뇌는 도구 결과를 다음 턴에 다시 받지 않는다, 제공자 교체·세션 교대 요약은 글만 넘긴다) 다시 열 수 있다. 교대 요약에 대화 저장소로 만든 "최근 주고받은 대화" 한 단락을 넣고, 교대 때 그 세션의 본 곳을 캐릭터의 읽음으로 되돌린다 | 제공자마다 기록 방식이 달라도 같은 결과가 나와야 한다([api-adapter-parity.md](api-adapter-parity.md)) |
| 비밀 대화 중 다른 알림 | 계속 온다 | 사적 모드 턴에는 업무 대화의 안 읽음 줄을 싣지 않는다. 업무로 돌아오면 읽은 위치가 그대로 보여 준다 | private-security, 이벤트 계획 `evt/D` |

## 보내기와 전하기

- 보내기는 하나다. 도구 인자는 대화, 본문, `reply_to`뿐이고 쪽지 전용 종류나 도구는 없다.
- "캐릭터 B에게 전해 줘"를 들은 캐릭터 A는 `dm:<A>:<B>`에 보낸다. 사용자의 1:1 입력에 쓴 `@B`는 텔레그램처럼 멘션일 뿐이며 엔진이 대신 배달하지 않는다. 전할지는 A가 듣고 판단해 보내기를 쓴다.
- 단체방의 `@`는 지금처럼 그 방 글의 멘션이고 발언자 선택에 쓰인다.
- 사용자↔캐릭터의 1:1에는 그 두 참여자만 쓴다. 다른 캐릭터가 그 대화에 글을 넣는 길은 없다. 오염이 구조적으로 막힌다.
- 사적 모드 세션에서는 보내기를 쓸 수 없다. 사적 대화의 내용이 업무 쪽 대화로 옮겨지는 길을 막는다(private-security T3).

## 범위

포함: 대화 id 규칙, 캐릭터끼리의 대화 로그, `msg.new` 업데이트 줄, (캐릭터, 대화) 읽은 위치, 안 읽음 수와 나를 부른 수, 턴 앞 대화 목록 한 줄, 보내기·불러오기 도구, `reply_to`, 화면 안 읽음 푸시.

하지 않는 것:

- 새 브로커, 웹소켓 서버, APNs/FCM.
- 받는 사람 수만큼 글을 복사하는 쓰기 쪽 팬아웃. 글은 대화 로그에 한 부만 있다.
- 이벤트 대장에 대화 본문 싣기([character-events-and-rooms.md](character-events-and-rooms.md)의 결정).
- 방 로그 형식 바꾸기. `reply_to`를 선택 키로 더하는 것만 한다.
- 사용자↔캐릭터 1:1을 새 저장소로 옮기기. 세션 기록이 그 대화의 저장소다.
- 수정·삭제·전달(forward)·반응. 답장의 화면 표시는 `ux/S7`이 맡는다.
- 이벤트 종류·수취인 규칙. 작업·재시작·예약 이벤트는 [character-events-and-rooms.md](character-events-and-rooms.md)가 정하고 지금처럼 같은 대장에 쌓인다.

## 의존·순서·리스크

순서: 0과 A(서로 독립) → B → C와 D(서로 독립, D는 0도 필요) → E(D6 결정 뒤).

리스크:
- `inbox/0`은 이 계획 밖의 도구에도 닿는 기반 작업이다. 어댑터마다 도구 연결 방식(CLI 설정 파일, HTTP 중계)이 달라 크기를 M으로 잡았다. 실패하면 D를 열지 않는다.
- 방 로그 모듈을 꺼낼 때 `room_chat`의 `seen`(멤버별 마지막 발언 위치)은 발언자 프롬프트용으로 남긴다. 읽은 위치(`inbox/B`)와 섞지 않는다.
- 대장은 30일·10MB에서 오래된 줄부터 지운다(E3). `msg.new`가 지워져도 본문과 읽은 위치는 대화 저장소 쪽에 있으므로 안 읽음 수는 대화 로그에서 다시 계산할 수 있어야 한다.
- 캐릭터 A가 B에게 보낸 글은 B가 턴을 돌 때 보인다. 바로 답하게 하려면 자동 반응(`evt/D`, E2 기본 꺼짐)에 `msg.new`를 켤 수 있는 종류로 더하는 별도 결정이 필요하다.
