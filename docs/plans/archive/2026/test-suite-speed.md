## 0. 결론 먼저

느린 게 아니라 **쏠려 있다.** 115개 중 **99개가 2초 미만**이다(합계 73s, 평균 0.73s). 전체 시간의 **58%가 상위 4개 모듈**에 있고, 그중 가장 큰 하나는 **같은 게이트를 8번 실제로 실행**하고 있다.

일일 루프의 레버는 "테스트를 더 빠르게"가 아니라 **"적은 것만 돌린다"**에 있다.

## 2. 비결정성 — "느려졌다"가 성립하지 않는다

같은 커밋을 **223 s / 232 s / 401 s**로 관측했다. 원인은 `test_tickets`가 **6.6 s ↔ 104 s**로 출렁이는 것:

`_guard_failure`는 `data`의 git root를 찾지 못하면 즉시 `""`를 반환한다. 그 테스트들이 만드는 임시 디렉터리가 git root인지에 따라 **19 s짜리 게이트를 실제로 돌릴지 말지가 갈린다.** 즉 스위트 비용은 상태에 따라 달라진다.

이건 두 가지를 같이 망친다. "느려졌다"는 감각이 신뢰되지 않고, 계층(`split/A`)처럼 보이는 오차가 사실은 ① 상태 의존 ② 프로세스당 고정비다.

## 3. 원인 (측정된 것만)

1. **게이트의 중복 실행** — `tickets.py::_guard_failure`가 티켓마다 가드 스위트를 실제로 돌린다. 코드가 스스로注释에 `~11 s`라고 적어 두었다. `test_tickets`가 그 경로를 8번 통과시킨다.
2. **모듈당 프로세스** — 격리 부채 때문이다. `monolith-split.md` `split/A`가 93/1,190을 측정했고, 그래서 `run-tests.sh`는 115개 프로세스를 띄운다. 고정 비용만 **35–40 s**.
3. **전체만 돌리는 관습** — 편집 → 확인 루프에 401 s. `--fast`(19 s)이 계약상으로는 커밋 전 게이트로 충분한데, 릴리스 전에는 전체가 요구된다.
4. **"관련 테스트만" 모드가 run-tests.sh에 없음** — 게이트 쪽에는 이미 있다: `tools/worktree_runner.py::related_gate`가 변경 파일을 관련 테스트에 매핑한다. 같은 장치가 개발 루프에는 없다.

## 5. 순서와 기대

`speed/A` → `speed/B` → `speed/C`, `speed/D`는 측정만이라 독립.

- **1순위는 `speed/A`**다. 가장 큰 이득(104 s → ~35 s 추정)·가장 낮은 위험·테스트 파일 하나만 건드린다. 그리고 `speed/A`가 §2의 출렁임도 같이 없앤다.
- **`speed/B`가 일일 레버가 가장 크다.** 편집 → 확인이 401 s에서 20 s + 관련 몇 개로 내려간다. `split/B`(라우터)나 `split/C`보다 먼저.Infrastructure보다 손해가 작다.
- **`speed/C`는 구조 해법**이다. 35–40 s를 이기지만, 진짜 값은 한 프로세스에서 돌릴 수 있어야 병렬화가 열린다는 점이다. 위험은 테스트 하네스에만 있고 프로덕션 코드에는 없다.

## 6. 여기서 하지 않는 것

### 6.1 전체 스위트를 줄이지 않는다

릴리스 전 전체 실행은 계약이다(루트 `AGENTS.md` "full suite before release"). 이 계획은 그 요구를 낮추지 않는다. **루프**에 필요한 런타임만 줄인다.

### 6.2 `speed/C`는 여기서 새로 정의하지 않는다

격리 부채의 원래 측정은 [monolith-split.md](monolith-split.md) Phase 6 §6.1과 `split/A`에 있다(93/1,190, 대문자 모듈 전역 42개, 되돌리지 않는 캐시 2개). **사실의 정본은 그 문서이고**, `speed/C`는 그것을 실행하는 항목일 뿐이다. 채굴하지 않는다.

### 6.3 `test_worktree_runner`·`test_delegation`을 느리게 만들지는 않는다

둘 다 실제 worktree·실제 위임을 스폰하는 계약의 대가다. `speed/D`로 성격을 먼저 재고, 대기라면 줄이고 작업이라면 둔다.

## 7. 열린 질문

- `run-tests.sh --changed`의 "관련" 기준을 `related_gate` 그대로 쓸지(`tools/`에 있는 현재 매핑) 더 넓힐지(예: `static/` 파일 변경은 UI 하네스 전체). 넓히면 `--fast`만으로 충분한 케이스가 늘어난다.
- `_guard_failure`의 중복을 줄일 때, 게이트를 **한 번만** 돌리고 결과를 테스트가 공유하는 구조가 맞는지, 아니면 게이트 호출 자체를 주입 가능하게 만들어 테스트에서 가짜를 넣을지. 후자가 더 정직하지만 `tickets.py`에 테스트용 훅이 들어간다.
- 전체 스위트를 병렬로 돌릴지(`TEST_PARALLEL=`, 모듈 간 의존이 없다는 전제 검증 필요). 격리 부채가 남은 상태에서는 안전하지 않다 — `speed/C` 뒤에나 가능하다.
