### 1.1 측정의 정의와 보정 (2026-10-04)

비교가 의미 있으려면 양쪽이 같은 방식으로 세야 한다.
- **정의:** `input_tokens` = 캐시를 뺀 새 입력, `cache_read_tokens` = 캐시에서 읽은 몫, `output_tokens` = 출력. 대화 기록과 위임 기록 모두 각 제공자 어댑터의 `normalize_usage` 한 곳을 거친다.
- **보정 실험:** 같은 CLI는 대화가 쓰는 스트림 출력과 위임이 쓰는 JSON 출력에서 같은 수를 낸다. agy 입력 47,265 대 47,263, claude 전체 입력 24,106 대 24,106(캐시 쓰기와 읽기 비율만 캐시 상태에 따라 다름), grok 입력 22,766 대 22,769에 캐시 12,032로 같음(grok의 total_tokens = 입력 + 캐시 + 출력이라 캐시는 입력 밖). codex는 대화와 위임이 같은 `codex exec --json`을 쓴다.
- **고친 것:** codex는 캐시 몫이 `input_tokens` 안에 들어 있는데(같은 질문 두 번: 입력 20,141에 캐시 2,816, 다음엔 0) 어댑터가 캐시를 따로 또 세어 두 번 셌다. 2026-10-04 이전 codex 대화 기록은 입력이 그만큼 부풀어 있다.
- **보고 규칙:** 합계 하나로 비교하지 않는다. 새 입력, 캐시 읽기, 출력을 따로 보여 주고, 비용 추정은 쓰는 가중치(예: 캐시 읽기 = 새 입력의 0.1배)를 함께 적는다.

## 2. 원인

1. **한 번 읽은 내용은 그 턴이 끝날 때까지 도구를 부를 때마다 모델에 다시 보내진다.** 그래서 40번 부르는 턴에서 1MB를 읽으면 수백만 토큰이 된다.
2. **기본 캐릭터(노노)가 `lead`와 `dev`를 함께 가져** 엔진 개발을 대화 세션에서 직접 했다. 위임하면 짧게 쓰고 버리는 작업 세션에서 일어날 일이다.
3. 큰 소스 파일을 범위 없이 통째로 읽는다(검색 후 필요한 줄만 읽지 않음).
4. 소스 파일 자체가 크다(80KB대 여럿).
