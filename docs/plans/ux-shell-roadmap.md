# UX 껍데기 로드맵 — 메신저 먼저, 데스크톱 캐릭터는 두 번째 껍데기

> 방향 (align/D, 2026-09-29): **핵심** — 메신저는 관계 고리를 검증하는 기본 UX이고, 데스크톱 캐릭터는 CONCEPT가 정체성으로 둔 「움직이는 데스크톱 동반자」다. 둘의 순서와 경계를 정한다

> 상태: **active** (2026-09-29 초안 · 2026-09-30 메신저 뼈대 결정 4.2.3)
> 목적: 메신저 UX를 먼저 "완성"하고 데스크톱 캐릭터 UX로 넘어가는 순서를 채택하되, ① 메신저 "완성"을 끝이 있는 기준으로 정하고 ② 엔진을 화면에서 떼어 두 껍데기가 같은 통로를 쓰게 하고 ③ 캐릭터 중심 밀도를 다리로 삼는다.

## 1. 운영자 제안 (2026-09-29)

"나중에 데스크탑 캐릭터 형태의 UX를 추가할 예정이지만 기본 UX는 메신저 형태. 메신저 형태를 완성한 후 캐릭터 UX에 들어가는 계획 어때?" → 조건부 찬성 후 "계획 문서로 정리해줘".

이어서: "메신저 측면에서 UX는 Telegram, Line, Kakaotalk 등의 Modern Messenger 앱을 따라가는 수준까지 다듬어야 해." → 4.2.1의 기준선.

이어서: "Steam 배포를 생각하니 steamdeck 호환성 확보도 가능하면 좋겠어. 데스크탑 말고 스팀덱에서 실행했을 때의 UX도 후보로 추가하는 거야." → 4.6. 플랫폼 쪽은 [platform-portability.md](platform-portability.md) DK1·`pp/I`.

이어서: "데스크탑 UX의 기준선은 https://github.com/tinyhumansai/openhuman 이 프로젝트가 좋겠어" → 4.4.1. "모바일 UX의 기준선은 https://github.com/drklo/telegram 모바일 텔레그램" → 4.2.2.

## 2. 판단

**순서는 채택한다.** 대화·기억·선택지·호감도 같은 관계 고리는 메신저에서 검증하는 편이 가장 싸다. 데스크톱 캐릭터에 필요한 재료(투명 스프라이트, 표정 대체 사슬, 그림 관리)도 메신저 작업 중에 쌓인다.

**그대로 두면 생기는 위험 두 가지:**

1. **데스크톱은 부속물이 아니다.** CONCEPT는 「움직이는 데스크톱 동반자」와 「Steam에 BYOK 데스크톱 동반자로 먼저 이름을 박는다」를 정체성으로 둔다. 시장 검토도 차별점을 "대화창 안에서 못 하는 것 = 데스크톱 형식"으로 본다. 메신저만으로는 제타·SillyTavern류와 겉모습이 겹친다. 그래서 순서는 뒤라도 날짜 없는 "언젠가"가 되면 안 된다.
2. **"완성"에 끝이 없다.** UI 다듬기는 끝나지 않는다. 기다리는 동안 채팅 화면(DOM)을 전제로 한 코드가 쌓이면 데스크톱을 붙일 때 뜯어고쳐야 한다.

## 3. 현황 (2026-09-29 코드 기준)

- **외형 통로는 있다.** `static/visual-adapter.js`의 `VisualAdapter`(`load`·`setEmotion`·`speak`·`destroy`)와 `AdapterRegistry`, 구현체는 `static/visual-sprite-adapter.js` 하나.
- **감정은 서버 이벤트다.** `emotion.py`가 답변의 표정 태그를 읽어 턴마다 `{"type":"emotion"}` SSE(서버가 브라우저에 밀어 주는 이벤트 흐름) 하나를 보낸다(`server.py`).
- **배달은 채팅 페이지에 묶여 있다.** `static/app-characters.js`가 브라우저의 `EventSource`를 가로채서 감정을 어댑터로 넘긴다. 이벤트 흐름도 세션 단위(`/api/sessions/<sid>/events`)다. 채팅 페이지를 열지 않은 데스크톱 껍데기는 지금 캐릭터 상태를 받을 길이 없다.
- `align/K`(게임 속 메신저 적용)는 대기 상태이고, 수용 기준은 "§5.1의 가르는 선 세 가지가 화면에 있고 테마 7종이 동작"이다.

## 4. 설계

### 4.1 두 껍데기, 하나의 엔진

식당으로 치면 주방(엔진)은 하나이고 홀(메신저)과 배달(데스크톱)이 창구다. 창구는 주방에 **정해진 주문서(이벤트)**로만 말하고, 주방은 어느 창구에서 온 주문인지 모른다.

- **캐릭터 상태 이벤트**: `emotion`·`speaking`(시작/끝)·`action`(지문)·`presence`(대기/생각 중/자리 비움)를 엔진이 캐릭터 단위로 낸다. 메신저와 데스크톱 모두 같은 이벤트를 구독한다.
- **화면 쪽 규칙**: 캐릭터 연출 코드는 `VisualAdapter`만 부르고 채팅 DOM(말풍선·로그)을 읽지 않는다. 반대로 채팅 코드는 스프라이트를 직접 만지지 않는다.
- **집행자**: 이 규칙은 테스트로 막는다(`ux/C`). `visual-*.js`가 채팅 DOM 선택자를 참조하거나 `EventSource` 가로채기가 새로 생기면 실패한다.

### 4.2 메신저 "완성"의 정의

메신저 완료 = 아래 체크리스트가 모두 참일 때. 이후의 다듬기는 데스크톱 작업과 **병행**하고 선행 조건으로 삼지 않는다.

1. **현대 메신저 기준선**(4.2.1)과 **모바일 기준선**(4.2.2)을 모두 통과한다.
2. `align/K`의 수용 기준(가르는 선 세 가지: 캐릭터가 대화에 끼어듦, 관계가 보임, 캐릭터별 개인화가 묻어남 + 테마 7종).
3. 세 밀도(① 캐릭터 중심 ② 심플 ③ 어드밴스드)를 오갈 수 있다.
4. 보스 키(순식간에 숨기기)가 동작한다.
5. 캐릭터 연출이 모두 4.1 이벤트로 돈다(`ux/B`·`ux/C` 완료).

#### 4.2.1 현대 메신저 기준선 (운영자 2026-09-29: Telegram·LINE·KakaoTalk 수준)

**기준은 "손에 익은 동작과 매끄러움"이지 모양이 아니다.** 사용자가 메신저에서 이미 익힌 동작은 그대로 동작해야 한다. 반면 겉모습은 D10(게임 속 메신저, 특정 앱 모양을 베끼지 않음, 평범한 채팅앱은 버림)을 따른다. 이 둘은 충돌하지 않는다. 기준선은 바닥이고, 게임 속 메신저가 그 위에 얹는 개성이다.

끝이 있게 하려고 목록으로 고정한다. 목록에 없는 것은 기준선이 아니다. 항목마다 세 앱 중 두 곳 이상이 가진 동작만 넣었다.

| 영역 | 기준선 동작 |
|---|---|
| 목록 | 대화방 목록(마지막 메시지 미리보기·시각·안 읽은 수), 고정, 검색 |
| 대화 흐름 | 날짜 구분선, 같은 사람 연속 메시지 묶기, 보낸 시각, 안 읽은 곳으로 이동·맨 아래로 버튼, 위로 스크롤하면 이전 대화 불러오기 — **읽음 표시와 "입력 중"은 동반자 방식으로 바꿈(4.2.1b)** |
| 메시지 동작 | 길게 누르기/우클릭 메뉴(답장·복사·삭제·다시 보내기), 답장(인용) 표시와 원문으로 이동, 반응(이모지), 실패 표시와 재전송 |
| 입력 | 여러 줄 입력과 Enter 규칙, 임시 저장(방을 나갔다 와도 남음), 붙여넣기·끌어다 놓기 첨부, 이모지·스티커 서랍 |
| 미디어 | 그림 미리보기와 전체 화면 보기(확대·넘기기), 링크 미리보기 |
| 대화 안 검색 | 방 안 검색과 결과로 이동 |
| 알림 | 다른 창일 때 브라우저 알림, 탭 제목의 안 읽은 수 |
| 몸감(feel) | 모바일 폭·키보드가 올라와도 입력창이 가려지지 않음, 보낸 메시지가 바로 뜸(낙관적 표시), 스크롤이 튀지 않음, 전환 애니메이션 200ms 안팎, 키보드만으로 조작 가능 |

**기준선이 아닌 것**: 음성·영상 통화, 채널·봇 플랫폼(캐릭터 여러 명과의 대화방은 `ux/O`로 따로 계획), 여러 기기 동기화, 종단 간 암호화, 스티커 상점. 동반자 제품에 필요해지면 따로 계획한다.

진행 방식: `ux/I`가 이 표를 현재 화면과 대조해 있음/부분/없음을 매긴다(갭 감사). 빈 칸이 `ux/D`의 쪼갠 티켓이 된다.

**요약**: 30줄 중 있음 5 · 부분 8 · 없음 17. 입력과 모바일 몸감은 이미 기준에 가깝고, 비어 있는 곳은 **대화 흐름의 표시(날짜·시각·묶기·읽음)**, **메시지 동작(메뉴·답장·반응·삭제)**, **대화방 목록**, **알림**이다.

**구조 관찰 (설계가 먼저 필요한 것)**:
- **대화방 = 무엇인가.** 지금 단위는 "캐릭터 × 모드(업무/사적)의 세션"이고, 목록은 세션 관리 탭에 있다. 메신저의 대화방 목록은 **캐릭터가 한 줄**(친구 목록)이어야 자연스럽다. 세션은 그 방 안의 기록 조각이 된다. `ux/D1`에서 먼저 정한다.
- **답장·반응은 화면만의 일이 아니다.** 인용한 원문과 반응을 캐릭터(두뇌)에게 어떤 글로 전할지 정해야 한다. 반응은 사적 모드의 호감도와도 이어진다([private-mode.md](private-mode.md)).
- **링크 미리보기는 사생활 문제다.** 미리보기를 가져오면 외부 사이트에 요청이 나간다. 사적 모드에서는 끄는 게 기본([private-security.md](private-security.md)).

#### 4.2.1b 상대는 사람이 아니다 — 메신저를 그대로 따르지 않는 곳 (운영자 2026-09-29)

운영자: "메신저를 따라잡길 원하지만 상대방이 사람이 아니라 가상의 존재라는 점에서 메신저의 기능을 그대로 답습할 이유는 없어. … 작성 중은 감정이입에 방해가 돼. 읽음 표시도 에이전트가 안 읽을 방법이 없는데 어떤 의미를 가지는지 모르겠네." → 아래 네 가지 모두 동의(2026-09-29).

1. **시간은 날짜로, 세션은 숨긴다.** 기본 화면에는 날짜 구분선만("오늘", "어제", "9월 27일 토요일" — `Intl`로 만들어 번역 가능). 세션은 두뇌의 기억 창 사정이지 관계의 단위가 아니다. 사용자가 일부러 새 대화를 시작했을 때만 얇은 구분, 자동 인계는 표시하지 않음. 세션 ID·[전환]·[가져오기]는 ③ 어드밴스드 밀도에서만(같은 기능은 세션 탭에도 있다).
2. **연속 메시지**: 사용자 쪽은 메신저처럼 촘촘히 묶는다(모아서 보내는 동작은 그대로). "새 지시를 받았어요…" 같은 업무 안내는 캐릭터 대화에서 빼고 3의 "듣는 중" 기척으로 대신.
3. **"작성 중" 대신 캐릭터의 기척**: 아바타·스프라이트가 "생각 중" 표정과 작은 말줄임, 오래 걸리면 캐릭터다운 대기 한마디(카드의 캐릭터별 대기 대사, 없으면 기본값). 캐릭터 상태 이벤트(`ux/B`)를 쓴다. "N초째 · 작업 중" 같은 계기판 정보는 어드밴스드 밀도에서만.
4. **읽음 표시는 넣지 않는다.** 실패·재전송처럼 사용자가 알아야 할 상태만 남긴다. (사적 모드에서 캐릭터가 일부러 답을 늦추는 연출은 관계 장치가 될 수 있으나 나중 이야기.)
- 덤(우선순위 낮음): 캐릭터가 긴 답을 짧은 말풍선 여러 개로 끊어 보내는 말투를 카드 설정으로.
5. **말풍선 꼬리말도 어드밴스드로** (운영자 2026-09-29): 토큰·모델 표시는 어드밴스드에서만. 복사·읽어 주기는 기본 화면에서 마우스를 올리거나 선택할 때만(터치 화면은 흐리게). **"⋯" 메뉴의 "자세히 보기" 스위치**가 어드밴스드 밀도의 첫 조각(`body.density-advanced`, 이 브라우저에 기억) — 세 밀도 전환(`align/K`)의 시작점. "N초째" 기다림 표시는 캐릭터 기척(3)으로 바꾸기 전까지 기본 화면에 남김.

**메시지 동작 (UX13)**

- 넣는 것: 메시지 메뉴(우클릭·길게 누르기: 복사·다시 보내기·삭제, 말풍선 위 실패 표시와 재전송), 답장(인용, 누르면 원문으로), 반응.
- **반응은 이모지 딱지가 아니라 짧은 행위다.** 메뉴 위쪽의 행위 줄("웃는다", "끄덕인다", 사적 방은 "머리를 쓰다듬는다" 등 방에 따라 다른 목록)은 행동 입력의 빠른 버튼이다. 누르면 행동으로 보내지고 캐릭터가 거기에 반응한다. 새 서버 형식이 필요 없다.
- **행위는 말풍선에 달지 않고 가운데 지문으로 통일한다.** 운영자: "행위는 그냥 일관적으로 … 말풍선 외의 지문으로 가운데 생기는 것으로 통일하는 게 낫지 않나. 내 행동에 반응하는 캐릭터가 몰입도가 있을 것 같아. 지금처럼 뭔가 달아주는 느낌은 아니야." 내 행동과 캐릭터의 지문(답변의 `*…*`) 모두 말풍선 밖 가운데 줄, 대사만 말풍선. (운영자 2026-09-30: "좋은 방향이야")
  - **열린 점**: 업무방 답변에서 `*…*`는 마크다운 강조이기도 하다. 지문으로 빼는 범위(사적 방의 `RENDER_PROTOCOL` 답변만 / 문단 전체가 기울임일 때만)는 `ux/S5`에서 정한다.
- 삭제는 화면과 기록에서 지운다. 진행 중인 세션의 두뇌가 이미 읽은 내용까지 잊게 하지는 못한다 — 메뉴 문구가 그렇게 말해야 한다.
- 빼는 것: 스티커 서랍(`ux/D9` 폐기), 이모지 반응. 4.2.1 표의 "반응(이모지)"·"이모지·스티커 서랍" 두 줄은 이 결정으로 기준선에서 빠진다.

**겉모습 (UX14): 스킨(앱) + 캐릭터(방) 두 겹**

운영자: "전체적 비주얼은 현재 대화중인 캐릭터의 이미지 리소스가 지배해. 키컬러를 둔 건 대화중인 모델을 직관적으로 인지시켜볼까 해서 도입한 거였는데 현재로서는 좀 애매해졌어. 어쨌든 전체적으로 다른 메신저만큼의 스킨이나 테마 기능은 있는 게 좋아."

- **스킨**: 사용자가 고른다. 앱 전체의 바탕·말풍선 모양·글자 크기. 밝은 스킨도 가능해야 한다. 스킨은 묶음 파일로 만들어 나중에 창작마당에 올릴 수 있게 한다([plugin-architecture.md](plugin-architecture.md)의 콘텐츠 플러그인).
- **캐릭터**: 자기 방의 강조색과 배경(무대 그림, [character-resource-pipeline.md](character-resource-pipeline.md) §10)을 얹는다. 강조색은 카드에 적거나 그림에서 자동으로 뽑는다.
- **업무와 사적은 분위기가 달라야 한다**(운영자). 시안: 사적 방은 어느 스킨에서든 조명을 낮추고 캐릭터의 색과 무대 그림이 방을 채운다. 색감 자체는 미정.
- **키 컬러 7종의 "모델을 알리는 색" 역할은 끝낸다.** 모델은 자세히 보기에서 글자로 보인다. 7종은 스킨의 재료로 흡수하거나 은퇴시킨다(`ux/S8`에서 정함). 이 결정은 D10의 "테마 7종 유지"를 바꾼다([direction-alignment.md](direction-alignment.md) §5.1에 기록).
- 방마다 사용자가 덮어쓰는 기능(Telegram식)은 첫 구현에 없다.
- **캐릭터 그림은 자기 기준으로 고정한다** (운영자 2026-09-30: "Provider에 따라 캐릭터 프로필 이미지가 달라지는 기믹이 … 다른 캐릭터 프로필에도 영향을 미쳐. 각자 자기의 현재 선택된 프로바이더 기준의 비주얼을 고정했으면"). 열린 캐릭터는 지금 고른 제공자, 나머지는 그 캐릭터와 마지막으로 쓴 두뇌의 그림(`static/app-characters.js::characterLook`, #482). 한 캐릭터가 여러 그림을 갖는 것은 가져가지만 **그것을 계속 제공자에 묶을지는 미정**(운영자 고민 중) — 묶는 기준을 읽는 곳을 `characterLook` 하나로 모아 두었다. `ux/S8`에서 정한다.

**스위치**: 새 뼈대는 스위치 뒤에서 만들었고(2026-09-30, `?shell=2`), `ux/S1`–`ux/S4`를 운영자가 확인한 뒤 **기본값이 됐다**(2026-10-01, #492). 옛 화면은 `?shell=1`로 그 브라우저에서 돌아갈 수 있고(`?shell=2`로 복귀), 허브의 compact 프레임은 옛 화면 그대로다(`static/index.html`의 첫 스크립트가 `html.shell2`를 붙임). 새 규칙은 모두 `html.shell2` 아래에 있어 옛 화면은 바뀌지 않는다(`tests/test_shell_page.py`). **남은 정리**: 옛 배치(탭 줄·트레이·스위치 자체)를 지우는 일은 `ux/S5`–`ux/S8`이 자리 잡은 뒤 한 번에 — 그때까지 옛 화면이 비상구다.

**대화 안에서 오가는 것의 종류** (운영자 2026-10-01, 참고로 받은 외부 글은 참고일 뿐): 말(say), 행동(action), 속마음(thought), 선택지(choices), 이동(move), 아이템(item). 지금 있는 자리 — 말·행동은 답변 분류(`static/app-blocks.js`)와 `/act`, 속마음은 ```` ```thought ```` 접이식, 선택지는 본문 밖 채널([out-of-band-choices-actions.md](out-of-band-choices-actions.md)), 이동은 `/private on <장소>` 명령 선택지([private-mode.md](private-mode.md) §8), 아이템은 [composer-plus-menu.md](archive/2026/composer-plus-menu.md)의 선물. 운영자 방향: 선택지는 LLM이 맥락에 맞게 만들고, 종류는 늘릴 수 있어야 한다. **열린 점**: 선택지에 말(say)을 넣는 것은 지금 사적 방 규약("선택지는 모두 행동, 말은 직접 입력")과 다르다 — 바꾸려면 그쪽 계획에서 결정. 이동을 선택지의 한 종류로 세우는 것도 장소 층(W3)과 함께.

**위임으로 바뀐 화면 (2026-10-01, #512–#525 — 계획에 빠져 있던 것을 #527 검토 때 기록)**: 기다리는 동안 중지 버튼이 타이핑 점 말풍선 안에 들어가고(#512) 작은 정지 원 아이콘으로(#514), 타이핑 점은 자세히 보기에서도 보임(#512 — 4.2.3의 "자세히 보기는 글자" 를 바꿈). 시스템 안내는 옆으로 밀어 닫음(#516). 얼굴은 목록 52px·대화 40px, 생각 말풍선 위치를 거기에 맞춤(#517). 목록 줄 간격을 줄이고(#518) 이름을 1.1rem으로(#519). 단체방 줄의 그림은 마지막으로 말한 멤버의 얼굴을 카드 더미 위에(#520). 목록 머리에 새 단체방(✎)·메뉴(☰) 아이콘, 목록 아래는 ⚙ 대신 **내 이름 줄**("접속 중", 누르면 설정)(#525 — UX11의 "목록 칸 아래 ⚙ 설정"을 바꿈). 0자 끼어들기는 흔적 없이(#518).

**순서**: `ux/S1`(뼈대) → `ux/S3`·`ux/S4`(머리·입력 바) → `ux/S2`(탭 이사) → `ux/S5`(지문) → `ux/S6`·`ux/S7`(메뉴·답장) → `ux/S8`(겉모습). 뼈대가 서기 전에는 나머지가 놓일 자리가 없다. `ux/S8`은 `align/K`와 한 작업이다.

### 4.3 다리: ① 캐릭터 중심 밀도를 앞당긴다

① 캐릭터 중심(캐릭터 + 말풍선)은 브라우저 안에서 하는 데스크톱 예행연습이다. 투명 스프라이트, 표정 전환, 말할 때의 연출, 대기 동작을 여기서 먼저 검증하면 데스크톱 껍데기는 "창을 바꾸는 일"로 줄어든다.

### 4.4 데스크톱 기술 스파이크 (짧게, 먼저)

스파이크 = 버릴 각오로 짧게 만들어 보는 기술 시험. 메신저 완료를 기다리지 않고 기간을 정해 한 번 한다. 확인할 것:

- 투명·항상 위·클릭 통과 창을 Windows/macOS에서 띄울 수 있는가, 어떤 셸(Tauri·Electron·기타)이 가벼운가.
- **엔진 위치**: 배포판은 사용자 PC에서 엔진이 돈다. 개발판은 엔진이 NAS에 있다. 데스크톱 껍데기가 둘 다에 붙는 연결 방식(로컬 주소·인증)을 정한다.
- 4.1 이벤트를 받아 스프라이트 하나가 표정을 바꾸는 데까지.

### 4.5 기준 저장소의 라이선스

두 기준 저장소 모두 GPL(openhuman GPL-3.0, Telegram Android GPL-2.0)이다. GPL 코드를 가져다 붙이면 우리 제품 전체를 같은 조건으로 공개해야 한다. 그래서:

- **동작과 설계만 참고한다.** 코드·그림·애니메이션 파일(openhuman의 `.riv` 마스코트 포함)은 복사하지 않는다. 필요한 동작은 문서(이 계획)로 옮긴 뒤 우리 코드로 새로 쓴다.
- Telegram 이름·로고는 쓰지 않는다(저장소 README의 요청).
- 집행자: `ux/J` — 저장소 안에 GPL 라이선스 헤더나 두 저장소의 식별자(`org.telegram.`, `openhuman`)가 코드에 들어오면 실패하는 테스트.

### 4.6 세 번째 껍데기 후보: 스팀덱 (운영자 2026-09-29)

스팀덱은 데스크톱도 모바일도 아니다: 7인치 1280×800 터치 화면, **게임패드가 주 입력**, 게임 모드에서는 전체 화면 앱 하나, 글자 입력은 화상 키보드(불편). 그래서 따로 다룬다.

- **어울리는 밀도**: ① 캐릭터 중심(캐릭터 + 말풍선)이 기본. 긴 글을 읽고 쓰는 메신저보다 "캐릭터와 마주 보는" 화면이 Deck의 쓰임(소파·침대)에 맞는다 — 비주얼 노벨 ADV에 가까워진다(D10에서 판단 근거로 남긴 후보).
- **입력**: 선택지(`choices`)와 액션을 게임패드 버튼으로(A 선택, 방향키 이동, B 뒤로). 자유 입력은 음성(두뇌가 STT를 쓸 수 있을 때) 또는 화상 키보드. 이미 있는 "선택지를 본문 밖 채널로"([out-of-band-choices-actions.md](out-of-band-choices-actions.md))가 여기서 큰 힘이 된다.
- **기준선 후보**: Steam Deck의 게임패드 UI 가이드(Steamworks "Steam Deck compatibility review" 항목: 기본 해상도, 게임패드 조작, 화상 키보드 호출, 글자 크기). Verified 배지의 체크 항목을 그대로 수용 기준으로 삼는다(실제 목록은 `ux/M`에서 원문 확인).
- **엔진은 같다**: 4.1의 캐릭터 상태 이벤트를 받는 또 하나의 껍데기. 데스크톱 껍데기와 대부분 공유(투명 창 대신 전체 화면).
- **Decky Loader 플러그인 (운영자 2026-09-29 제안)**: Deck의 빠른 접근 메뉴(QAM)에 붙는 커뮤니티 플러그인 틀(프런트엔드 React + 백엔드 Python, 전용 플러그인 스토어). 게임 중에도 QAM을 열면 캐릭터가 있고, 짧게 말을 걸거나 선택지를 누를 수 있다 — "게임하는 옆자리의 동반자". 엔진은 같은 기기의 PE 서버에 붙는 또 하나의 가벼운 껍데기(4.1 이벤트 + 메시지 보내기). 확인할 것: Decky는 Steam 공식이 아니라 별도 설치가 필요하고(Steam 페이지에서 기본 기능으로 내세울 수 없음), 플러그인 백엔드 권한이 높아 스토어 심사·보안 기준이 있다 — 원문 확인은 `ux/N`에서. 게임 모드의 PE 본체와는 별도 배포물.
  - **유입 경로로서의 가치 (운영자 2026-09-29)**: Deck 사용자 다수가 Decky를 쓰므로, PE를 모르던 사람에게 플러그인 스토어가 **발견 지점**이 된다 — [market-direction-review.md](market-direction-review.md) "이미 모인 곳으로" 원칙과 같은 방향. 확인 전 가정 두 개: ① 규모("거의 모든 사용자")는 스토어 설치 수 등 공개 숫자로 잰다 ② 스토어가 유료 본체로 안내하는 플러그인·외부 서버 연결을 허용하는지 원문 확인. 설계 원칙: **플러그인 혼자서도 쓸모가 있어야 한다**(기본 캐릭터 하나 + 사용자의 구독·무료 한도로 짧은 대화), 그 안에서 "더 깊게는 PE 본체"로 이어진다 — 체험이 곧 입구.
