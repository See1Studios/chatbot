resolution: |
  Root cause found (not what the Issue section guessed): `chatbot-ctl.sh`'s
  `kill_orphan_agy()` treated ANY agy process lacking `--conversation` in its
  args as a leftover doctor-probe and SIGTERM'd it unconditionally. But a
  brand-new real session's *first* turn also has no `--conversation` yet
  (only learned from agy's own output after the first reply), so any
  first-turn agy process running when the periodic doctor sweep (every
  ~600s) fires is indistinguishable from a probe leftover and gets killed —
  far more likely to get caught on `/skill` turns specifically because they
  take 30-40s (extra `view_file` + `npx` tool calls) vs ~9s for plain chat,
  giving a much wider window to collide with a sweep. Confirmed by adding a
  `debug_stderr_tail` field to `AgySession.to_public()` (server.py) which
  caught the real error `"stream input cancelled: context canceled"` on a
  run that still completed a full valid answer before dying — proving the
  kill happened *after* real work, not a `/skill`/npx-specific crash as
  originally hypothesized. Fix: added a 90s grace period (`NO_CONV_GRACE_SEC`)
  to the "no-conversation" kill branch in `kill_orphan_agy()`
  (`chatbot-ctl.sh`), using `ps -eo ... etimes= ...` to only kill
  conversation-less agy processes older than the grace window. Verified live:
  manually ran `chatbot-ctl.sh doctor` mid-flight during a real in-progress
  `/skill korea-weather` turn (agy pid confirmed running without
  `--conversation` at t+5s) — doctor no longer killed it
  (`orphan_agy_killed=0`), and the turn completed normally with `alive: true`
  afterward (previously: `alive: false` + no reply). No server.py restart was
  needed — `chatbot-ctl.sh` is a standalone script re-read on each invocation.

**Issue:** Live-tested via the real HTTP API (not a synthetic guess): a plain chat message (`한 단어로만 대답: 안녕`) completes normally in ~9s with an assistant reply. Sending `/skill find-skills <question>` or `/skill korea-weather 서울 날씨 알려줘` instead produces **zero assistant history entries** — the session's `busy` flag eventually flips to `false` (and for korea-weather, `alive` becomes `false`, i.e. the agy subprocess actually died) but no text or error is ever recorded. `db_bytes` grows substantially (49KB → 380KB for korea-weather), so real work happened. The conversation transcript (`~/.gemini/antigravity-cli/brain/<cid>/.system_generated/logs/transcript_full.jsonl`) for the korea-weather case shows only 2 steps: the user input, then a `view_file` tool call reading the skill's `SKILL.md` — which turns out to be a thin "k-skill cli-stub" (`<!-- k-skill:cli-stub — generated by scripts/generate-skill-stubs.js -->`) whose real instructions require running `npx -y @nomadamas/k-skill@0 instruct <name>` as a follow-up tool call. That follow-up command never appears in the transcript — the process dies between reading the stub and running it. Running the exact `npx` command manually in a plain shell (same PATH the server uses) succeeds in a few seconds and returns full instructions, so the npx/network path itself is not broken; something about the agy stream-json wrapper crashes specifically on this stub→shell-out pattern. (Root cause not further isolated: directly re-invoking `agy` standalone for isolated debugging was blocked by the harness's "Create Unsafe Agents" classifier, so this is reported at the bounded point rather than fully root-caused.)

**Suggested improvement:** Before trusting the `/api/skills` "popular" picker (10 skills incl. korea-weather, geeknews-search, etc. wired in `server.py`'s `do_GET /api/skills` handler) as functional, add a synthetic per-skill smoke test (send `/skill <name> <trivial arg>`, assert a non-empty assistant reply within N seconds) to `chatbot-ctl.sh doctor` or a dedicated `probe-skills` subcommand — `probe_message` today only exercises plain chat, so it cannot catch this class of failure. Root-cause candidates worth checking first: (a) does the stream-json protocol wrapper's stdin/stdout framing assume the model's next tool call arrives within some inferred timeout that a `run_command` calling out to `npx` (cold npm resolve) can exceed; (b) does `--dangerously-skip-permissions` interact oddly with a nested `run_command` whose output is itself long (help text + curl example) in a way that corrupts the stream-json output framing.

**Principle:** A skill-picker UI that lists skills as "available" is not evidence they work — cli-stub-style skills (thin `SKILL.md` that shells out via `npx`/similar to fetch real instructions) add a shell-out step to every invocation, and a streaming single-stdin agent wrapper needs to be explicitly verified against that pattern (not just plain chat) before the picker can be trusted; a chat-only healthz/probe misses an entire class of failure that only appears once a tool call chains into another tool call.
